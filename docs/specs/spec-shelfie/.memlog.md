topic: Shelfie: self-hosted pantry tracker PWA with per-lot expiry alerts and offline capture
updated: 2026-11-05T09:45
---

- (direction) Slug shelfie. Public MIT repo github.com/solomon234/shelfie; spec lives in the repo under docs/specs; BMad tooling (_bmad/) is gitignored.
- (decision) Why: Solomon wants expiry tracking that nudges him before food goes off and capture that works in a store with no signal; surveyed self-hosted options (GhostPantry, Pantry Host, Grocy, EverShelf, Pantrie): none confirmed to combine per-lot expiry, alerts and offline sync, so build own.
- (decision) Stack: Hono + Node 24 + SQLite via node:sqlite + Preact/Vite, one Docker image, multi-arch (amd64+arm64) published to GHCR by GitHub Actions; deployed on a Jetson via private Gitea pantry-deploy repo.
- (capability) CAP-1 Secure setup and accounts: first-run admin setup gated by SHELFIE_SETUP_TOKEN; users, households, memberships, login sessions.
- (capability) CAP-2 Inventory lots: record each package as its own lot with location, quantity, unit and optional expiry; consume, move and adjust.
- (capability) CAP-3 Barcode capture: scan with phone camera, normalize UPC-A/EAN-13, look up name/brand/image via Open Food Facts, manual entry fallback.
- (capability) CAP-4 Expiry visibility and alerts: dashboard of expired and expiring lots; per-household warning window; daily alert via ntfy or generic webhook, deduplicated.
- (capability) CAP-5 Shopping list: add items manually or from inventory, tick off, shared per household.
- (capability) CAP-6 Offline capture and sync: with no connection open the app, see last-known stock, scan/add/consume; changes queue on device and replay idempotently when online; unresolved barcodes show as pending until the server names them.
- (capability) CAP-7 Installable PWA: installable on Android and iOS home screen, app shell opens offline.
- (capability) CAP-8 Self-hosted operation: single container, SQLite on local volume, versioned migrations, health endpoint, multi-arch image, consistent backup.
- (constraint) Offline replay: iOS has no Background Sync, so replay on the online event and on app open.
- (constraint) Every queueable write carries a client-generated id; server idempotent per (household_id, client_id), scoped not global.
- (constraint) Camera needs HTTPS; deployment supplies it (Tailscale serve or reverse proxy); not the app's job.
- (constraint) SQLite WAL requires a local disk, never NFS/SMB; backups use SQLite .backup, not file copy.
- (constraint) Tenant isolation: every row scoped to a household; composite foreign keys forbid cross-household references (lot.location must share lot.household).
- (constraint) Schema changes only via ordered migrations tracked by PRAGMA user_version; never destructive to existing volumes.
- (constraint) Dates are ISO YYYY-MM-DD enforced by CHECK(date(x)=x); timestamps stored in one format (ISO 8601 UTC) to keep string comparison valid.
- (constraint) Unknown /api/* returns JSON 404, never the SPA shell; unauthenticated surface limited to health and setup/login.
- (constraint) Public repo: no secrets or host-specific config committed; deployment values live in the private pantry-deploy repo and env vars.
- (constraint) Barcodes normalized to EAN-13 form before lookup and as the unique key.
- (decision) Non-goals v1: native push notifications, receipt import, Home Assistant integration, native apps, recipes and meal planning, price tracking, hosted multi-tenant SaaS.
- (decision) Success signal demo: installed on a phone in airplane mode, scan three items with expiry and consume one; reconnect and they appear exactly once on a second device; an item expiring tomorrow produces one ntfy message next morning; a fresh instance cannot be claimed without the setup token.
- (assumption) Open Food Facts is the only product source, called server-side with a descriptive User-Agent; offline scans queue the raw barcode.
- (assumption) One timezone per household drives expiry day boundaries and alert time.
- (assumption) Offline consume is queued as a delta (decrement), not an absolute quantity.
- (question) Household timezone and alert time of day: configurable per household, default?
- (question) Offline consume conflict: lot already consumed on another device; apply delta floored at zero and surface a notice, or reject?
- (question) Roles: can members delete lots, invite users, change warning window, or only admins/owners?
- (question) Alert dedupe: notify once per lot per state change (entering warning window, expired), or daily until resolved?
- (question) Lots without a barcode: create products by name (case-insensitive match) or free-text lots?
- (question) Data portability: is SQLite file backup enough for v1, or is JSON/CSV export required?
- (direction) The existing scaffold on main predates these decisions: its schema needs a migration to composite FKs, CHECKs and scoped client_id; adversarial review findings are incorporated as constraints or stories.
- (assumption) Companion details are proposed design, not user-confirmed: POST /api/sync batch endpoint, alert_state table, household timezone and alert_hour columns, role names, UUID v4 client ids, hashed session tokens, rate and body-size limits.
- (decision) Alerts fire once per lot per state transition (warning, expired); supersedes the earlier open question on dedupe, which narrows to whether unresolved lots re-alert.
- (question) Should an unresolved warning or expired lot re-alert (for example a daily reminder), beyond the once-per-transition default?
- (constraint) Offline consume conflict handling is NOT decided: the constraint states only the delta; conflict behavior stays an open question.
- (decision) Stack conventions added from review: startup fails clearly on missing frontend, unwritable data dir, invalid PORT; release tags v*.*.*; GHCR package public; tests cover schema constraints, FK enforcement, SPA fallback, API 404, replay idempotency, migrations.
